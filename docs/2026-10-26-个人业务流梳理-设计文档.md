## 1. 目标与成功标准

### 1.1 目标

面向 FDE 进场后的客户业务员，在已填写《个人工作事项填写表》的前提下，用任意大模型对话完成：

1. **个人 SOP**：把「一行工作事项」整理成可照做的作业说明与流程图  
2. **技术落地准备**：为 RPA / AI 机器人提供系统触点、规则、异常与自动化边界  
3. **知识库准备**：在业务员确认后，派生可入库的条目卡与规范流程文档  

### 1.2 成功标准

| # | 标准 |
|---|------|
| 1 | 业务员带填好的 Excel，**尽量少追问**即可看到完整流程整理结果（对话中呈现） |
| 2 | 每条业务流：先 MD 主稿，再导出 Word；**Word 为最终确认文档** |
| 3 | **未确认不定稿、不入库**；改动以业务员意见为准，回写 MD 后再出确认稿 |
| 4 | 确认后可派生：系统与数据触点、自动化候选分析、知识库条目卡 |
| 5 | 统一目录收件，FDE 可直接用于机器人落地与知识库建设 |
| 6 | **不绑定 Cursor**；员工端任意 AI 可用；Cursor Skill 仅为 FDE 可选封装 |

## 2. 已锁定前提

| 项 | 约定 |
|----|------|
| 操作者 | 客户业务员**自助**与 AI 沟通；FDE 发材料、收件、补导出与归档 |
| 运行环境 | **豆包工作台、DeepSeek Harness、Cursor、普通网页对话等**（见 `业务流梳理包/05-多平台使用指南.md`）；规则一套、挂载方式不同 |
| 清单来源 | **先填 Excel**，再进入本包；清单不是 AI 从零虚构 |
| 选题节奏 | 基于表内明细 + 痛点速填，引导选「最值得」或按顺序深挖 |
| 提问策略 | 对齐需求评估：**少问、从已有信息尽量补全**；阻塞级缺口才追问 |
| **少问前提** | **必须先具备「行业 → 企业业务范围 → 部门 → 岗位 → 个人事项」上下文**（见 §2.1）；缺层则先补上下文，不假装能少问 |
| 呈现 vs 确认 | 沟通过程中该展示的整理结果**必须呈现**；Word 仅作**最终确认**载体 |
| 生成顺序 | **先 MD，再 Word**（MD 最快；Word 适合业务员阅读确认） |

### 2.1 少问成立的上下文链（硬前提）

能「少问多补」，靠的不是猜，而是补全时有可对齐的业务坐标系：

```
行业
  → 企业业务范围（做什么生意、对谁交付）
    → 部门职责与协作位置
      → 岗位职责
        → 个人工作事项（本包深挖对象）
```

| 层级 | 信息要什么 | 优先来源 | 缺失时 |
|------|------------|----------|--------|
| 行业 | 所属行业/细分赛道 | **用表内「公司名称」公网检索**（工商/官网/招聘/新闻等公开信息） | 检索无结果或互相矛盾 → 业务员一句话确认，或 FDE 补《企业上下文卡》 |
| 企业业务范围 | 主营产品/服务、主要客户类型、核心价值链一句话 | **同上，公网检索归纳**；项目内已有 `01-客户基本信息` 可直接用 | 同上 |
| 部门 | 部门名、人数、业务量基线、系统清单、岗位编制 | **`组织信息填写表`**（负责人填） | 无部门表则补问或暂缓深挖 |
| 岗位 | 岗位名、是否直接处理业务、主要职责 | 组织表 `02岗位编制` + 个人表 `01` | 与个人表互核 |
| 个人事项 | 触发/步骤线索/系统/异常/痛点 | **`个人工作事项填写表`** | 本包主输入，不可缺 |

**规则：**

1. 阶段 0：从组织表/个人表取出**公司名称** → **公网检索**归纳行业与业务范围 → 合成「企业-部门-岗位上下文」摘要 → **对话中出示**，请业务员一眼过（不对再说）；不必默认让业务员手填企业介绍。  
2. 进入阶段 3 前，上述上下文摘要必须已建立并呈现。  
3. 补全步骤/异常/系统时：先对齐该上下文 + 组织表系统/产物清单；禁止脱离行业与部门职责编造流程。  
4. 公网结论须标注「来源：公开检索，待业务员确认」；与业务员纠正冲突时**以业务员为准**。  
5. 仅有个人表、检索也补不出企业画像、又无组织表时：**不算具备少问前提**——先补齐再少问。  
6. 成套关系：默认 **1 份组织信息表 + 若干个人表**；《企业上下文卡》仅为检索失败/需纠偏时的可选材料，非人人必填。  
7. 运行环境若**不能上网检索**：FDE 事先检索写入上下文卡或客户基本信息再发给业务员侧 AI；提示词写明「无检索能力时改读已提供的企业材料」。

## 3. 整体方案

采用 **双层交付包（方案 2）**：

- **对业务员**：可移植「业务流梳理包」（使用说明 + 系统提示词 + 阶段补丁）  
- **对 FDE**：收件校验、Word 导出约定；可选 Cursor Skill 封装（读 xlsx、建目录、跑 docx）  

**与公开 process-doc / SOP Generator / RPA Assessment 的关系：**  
取其「写全什么」（SIPOC、过程要素、As-Is、异常与交接、轻量 RACI、自动化打分）；  
守我「怎么交付」（进场 Excel 先行、少问多补、公司名公网补上下文、对话呈现、MD→Word 确认门禁、确认后再派生 03～05、不绑 Cursor）。  
详见 `业务流梳理包/04-公开方法与对标.md` §0。

不采用「单段万能提示词」作为唯一正式形态（易跑偏、难保证 Word/目录）。  
不采用「纯问卷无对话」为主路径（与现有 Excel 进场表重复，且缺呈现与确认闭环）。  
不采用公开 skill 默认的长访谈主路径。

## 4. 阶段机（Excel 驱动）

```
阶段 0  取公司名称 → 公网检索行业/业务范围 → 叠加组织表+个人表 → 出示上下文摘要
         （检索失败再少问或改用已有客户材料）
   ↓
阶段 1  回读个人表 02 明细（对照组织表岗位/系统/业务量）→ 阻塞才问；其余补全并标待确认
   ↓
阶段 1b 对照个人表 03 痛点速填，对齐优先级；对话中出示确认版清单
   ↓
阶段 2  引导选题：按痛点推荐 / 按顺序 / 业务员自选
   ↓
阶段 3  单条深挖：在「行业-企业-部门-岗位」坐标系内补全；对话呈现 SOP 与流程图
   ↓
阶段 4  输出该流 MD 全套草稿 → 导出 Word 确认稿 → 业务员最终确认
   ↓
阶段 5  确认通过后派生 03～05；清单打勾 → 下一条 / 交件
```

### 4.1 输入映射

| 来源 | 用途 |
|------|------|
| 公司名称 → 公网检索 | 行业、业务范围、公开画像（主路径） |
| 项目内 `01-客户基本信息` / 企业上下文卡 | 检索结果缓存、纠偏或无网环境备用 |
| 组织表 `01基本信息与配合` | 公司、部门、人数、配合与 SOP 收集情况 |
| 组织表 `02岗位编制` | 岗位树、是否直接处理业务、职责一句话 |
| 组织表 `03业务量基线` | 部门级事项与量级（和个人事项对齐用） |
| 组织表 `04系统与产物清单` | 补全「系统/工具」时的权威清单 |
| 个人表 `01填写人信息` | 姓名、岗位、服务对象、最希望少做的事 |
| 个人表 `02工作事项明细` | 一行 ≈ 一条候选业务流 |
| 个人表 `03痛点速填` | 默认推荐选题顺序 |
| 两表填写说明 | 脱敏与填写规范 |

说明：表内素材 **不等于** 已确认流程。确认对象仍是整理后的 Word 确认稿。

### 4.2 提问边界（少问多补）

**在 §2.1 上下文已齐的前提下**：默认不问，按表格 + 公网归纳的行业常识 + 部门材料补全草稿。

**上下文未齐时**：优先用公司名检索；仍齐不了再极少补问或读 FDE 已备材料；**不要**在上下文空洞时连环追问步骤细节。

进入深挖后，仅在下列**阻塞级**情况追问（尽量合并）：

- 事项名/触发完全对不上，无法选定对象  
- 完全无法判断在哪个系统/载体上操作，且组织表系统清单也对不上  
- 痛点 Top3 与明细严重错位，必须先确认是否同一件事  

其余不确定处写入正文「待确认/假设」，在对话呈现，并由 Word 确认收口。

### 4.3 呈现与确认

```
Excel（主输入）
   ↓
AI 尽量补全 → MD 草稿
   ↓
对话中呈现（清单、SOP 要点、流程图等）← 可口头纠错并回写 MD
   ↓
导出 Word 确认稿 ← 最终确认 / 签字级认可
   ↓
确认通过：冻结确认版 MD + Word
   ↓
派生知识库条目、自动化分析等（基于确认版 MD）
```

- 口头纠错可在出 Word 前发生并回写 MD  
- **「已确认」状态**以业务员对 Word 确认通过为准  
- 未确认：不定稿、不覆盖入库类派生件

## 5. 目录与文档清单

### 5.1 总目录

```
{公司}-{部门}-{姓名}-业务流梳理/
├── 00-企业与部门上下文摘要.md        # 行业 → 业务范围 → 部门 → 岗位
├── 00-岗位业务清单（确认版）.md
├── 00-填写人信息摘要.md
├── 原始表-组织信息填写表-….xlsx      # 若有
├── 原始表-个人工作事项填写表-….xlsx
├── 企业上下文卡.md                   # 若有
└── flows/
    ├── 01-{事项短名}/
    ├── 02-{事项短名}/
    └── …
```

文件夹命名：序号与清单一致；短名由事项名压缩；避免空格与特殊符号；过长约截断 20 字。

### 5.2 单条业务流目录

```
flows/01-{事项短名}/
├── 00-事项原文与确认.md           # Excel 该行原文 + 补全/待确认 + 确认后状态
├── 01-业务流程图.md               # Mermaid 主流程 + 异常分支
├── 02-SOP作业指导书.md            # 主稿（AI 优先写）
├── 02-SOP作业指导书-确认稿.docx   # 由 MD 导出，给业务员最终确认
├── 03-系统与数据触点.md           # 建议确认通过后再定稿生成
├── 04-自动化候选分析.md           # RPA / AI / 人工边界；确认后
├── 05-知识库条目卡.md             # 确认后
└── 确认记录.md                    # 谁、何时、通过或修改要点
```

### 5.3 相对 Excel 一行，定稿应具备的深度

1. 步骤拆到可照做（谁、在哪个界面/表格、做什么）  
2. 主路径 + 至少常见异常分支（由表内「最常见出错」展开）  
3. 输入/输出物清单（脱敏）  
4. 判断规则可执行化（避免长期停留在「看情况」）  
5. 自动化边界（不可自动处、必须人审处）  

### 5.4 Word 确认稿必备内容与阅读顺序

**第一要义**：业务员直观确认 AI 梳理是否正确 → **流程图必须最先、最大呈现**。  
**第二要义**：FDE 打开业务流文件夹时，凭该 Word 快速理解整条业务。

固定顺序：

1. 事项标识（名称/岗位）+ 短确认提示（请先对图）  
2. **一、业务流程图（图，主视觉）**  
3. 二、业务背景（目的、SIPOC、触发、完成标准等）  
4. 三、操作步骤与协作  
5. 四、异常与待确认  
6. 文末确认提示  

禁止流程图放文末或附录。图须为渲染图（不仅 Mermaid 源码）；出图失败时仍保留「一、业务流程图」章节占位。  

### 5.5 Word 落地（环境不统一时）

1. 当前 AI 能下发 `.docx` → 按约定导出确认稿  
2. 不能 → 对话中仍完整呈现 MD 内容；由 **FDE 用同一 MD 跑导出** 出正式 Word 发回业务员  
3. 确认方式：回复「确认」/ 批注修改点 / 回传改过的 Word → 回写 MD → 再导一版复确认  

**确认稿不可长期空缺**；不能把「只看聊天记录」当作最终确认完成。
